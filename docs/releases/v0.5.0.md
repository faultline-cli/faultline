# Faultline v0.5.0

Faultline v0.5.0 introduces the Teams authentication layer — the first
milestone toward cross-run coordination and organizational features — while
expanding test coverage and fixing a security issue in the new HTTP client.

## What This Release Delivers

- **`faultline auth` command** — A new `auth` subcommand group provides
  interactive and non-interactive authentication against the Faultline Teams
  API. Subcommands: `login`, `logout`, `status`, and `token set`.
  - `faultline auth login` — Authenticates via email/password and stores a
    persistent `ft_…` API token at `~/.config/faultline/credentials` (0600).
  - `faultline auth logout` — Removes stored credentials (idempotent).
  - `faultline auth status` — Verifies the stored token against the API and
    prints the authenticated identity.
  - `faultline auth token set` — Stores an API token directly; suitable for CI
    environments where interactive login is not possible. The `$FAULTLINE_TOKEN`
    environment variable is also accepted as an alternative.
- **`internal/teams` package** — New package encapsulating Teams API client
  (`client.go`) and credentials persistence (`config.go`). Credentials are
  stored with owner-only permissions (`0600` file, `0700` directory) following
  the XDG Base Directory Specification.
- **Security fix** — Error response bodies in the Teams HTTP client are now
  read through `io.LimitReader` (4 KiB cap), preventing a malicious or
  misbehaving server from exhausting memory via an unbounded response body
  (OWASP A10).
- **Test coverage expanded** — 32 new tests across `internal/teams` and
  `internal/cli`:
  - `internal/teams/config_test.go` — credentials round-trip, file and
    directory permissions, XDG path resolution, missing-file nil-return,
    idempotent clear, and corrupt-JSON error handling.
  - `internal/teams/client_test.go` — Login success/failure paths, token
    creation failure, large error body truncation, VerifyToken happy/unhappy
    paths, and HTTP client timeout assertion.
  - `internal/cli/cmd_auth_test.go` — logout (clear and idempotent), status
    (not logged in, valid token via mock server, expired token, empty token),
    token set (prefix validation, storage, `--api-url` flag, `$FAULTLINE_API_URL`
    fallback, default production URL), and command wiring assertions.
- **Release-boundary manifest updated** — `auth` and its subcommands are
  registered in `CommandSurfaces` as `SurfaceCompanion / MaturitySupported`,
  consistent with `report`.

## Release Validation

v0.5.0 should be validated with:

- `make test`
- `make fixture-check`
- `make bayes-check`
- `make review`
- `make docs-check`
- `make cli-smoke`
- `make release-check VERSION=v0.5.0`

## Release Boundary Status

The default user story is:

- `analyze`
- `batch`
- `workflow`
- `list`
- `explain`
- `fix`
- `inspect`

`report` and `auth` are supported companions. All `fixtures *` commands remain
hidden maintainer utilities.
